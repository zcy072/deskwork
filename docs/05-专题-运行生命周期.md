# 05 专题:运行生命周期、回退与版本

Agent 一轮可能跑几分钟。这期间会遇到:请求重复提交、同一会话并发发送、用户中途取消、浏览器断线、进程重启,
以及用户想回到某一轮之前重来。本文说明系统在每种情况下怎么保持一致(代码在 `services/chat_operations.py`)。

## 1. 先记住一个设计

**Agent 的运行和浏览器连接是解耦的。** 发送消息只登记一个持久的 `Run`、启动后台任务并返回 `prompt_id`;
事件写进 Redis Stream;前端另开一个连接去读。所以断线、刷新、关页面都不影响运行。

```
前端 ──POST /send-message──►  start_chat ──► Run 落库(accepted)──► 启动后台任务 ──► 返回 prompt_id
                                                  │
                                                  ▼ 每个事件(带 run_id / seq)
                                          Redis Stream(prompt_id) + 定时保存的 Message 快照
                                                  ▲
前端 ──POST /stream-events(start_id)──────────────┘  读取,可随时断开重连
```

状态分三处,各管各的:

| 位置 | 管什么 |
|---|---|
| 业务 SQLite 的 `runs` 表 | 请求是否被接受、`client_request_id` 幂等、运行状态、错误、用量、逻辑轮次(`turn_id`)、恢复关联。**持久**,重启后仍在 |
| 进程内的 `SessionRegistry` / `RunHandle`(`runtime/sessions.py`) | 实际的 asyncio task、取消标志、`preparing → running → finalizing` 阶段、`recovery_required`,以及"同一会话同时只有一个操作"的占用 |
| Redis Stream | 只做短期进度传输和按游标续读。新运行的状态和归属**不再依赖** Redis 的状态键 |

`RunHandle` 和占用只在本进程内有效,所以后端仍只能单进程部署。

### 1.1 几个标识符

| 名字 | 是什么 | 谁用 |
|---|---|---|
| `session_id` | 会话和工作区 | 贯穿全部 |
| `prompt_id`(= `run_id`) | **一次执行**的 id,每次发送新生成 | `Run` 主键、事件流的键、快照目录名、消息记录 |
| `turn_id` | 逻辑轮次:一次任务加上它后续的人工回答 | 预算按轮累计 |
| `client_request_id` | 前端为一次发送生成的 id | 幂等,会话内唯一约束 |
| 条目 id(如 `1730000-0`) | Redis Stream 给每个事件的编号 | 前端断线续传的断点 |
| `seq` | 应用层事件序号 | 前端去重、快照对齐 |

LangGraph 的 `thread_id` 默认等于 `session_id`,但回退可能把会话切到新的 thread(§5),
当前选中的 thread/checkpoint 记在 `Conversation.graph_thread_id/graph_checkpoint_id`;工具从 `RunContext.session_id` 取工作区身份。

### 1.2 Run 的状态

| 状态 | 含义 |
|---|---|
| `preparing` | 已接受,正在做回退、快照、恢复点选择等准备 |
| `running` | 图正在执行 |
| `finalizing` | 正在收尾(关闭流、补工具结果、落库) |
| `complete` | 本轮结束 |
| `waiting` | 本次执行停在向用户提问上;图已持久暂停,**不占着任务** |
| `error` / `cancelled` | 出错 / 被用户取消,带 `error_code` 和对用户可读的 `public_error` |

前三个是"进行中"。`GET /thread-status/<id>` 组合当前 handle 和最新 Run 返回状态;handle 处于 `recovery_required` 时返回 `error`。

## 2. 启动一轮

`start_chat` 只做"接受"这一步,真正的准备在后台任务 `_run_agent` 的开头完成。

```
 start_chat:   ① 幂等 ──► ② 占用会话 ──► ③ 归属/回退目标/快照是否可用 ──► ④ 上传 ──► ⑤ Run 落库 ──► ⑥ 启动任务
 _run_agent:   ⑦ 回退(staging→journal→安装)/选恢复点 ──► ⑧ 输入提交(用户消息+图选择,一个事务)──► ⑨ 快照 ──► 运行
```

**① 幂等。** 前端每次发送带一个 `client_request_id`,指纹是消息文字、回退目标与模式、interrupt_id、每个上传文件的内容摘要和文件名
(上传可达 100 MB,哈希放进线程)。查 `runs` 表:

- 同 id、指纹相同:直接返回原来的 `prompt_id`。
- 同 id、指纹不同:拒绝(`RequestIdConflictError`)。
- 记录持久保存,重启后仍有效。发送响应丢失时,前端按 `GET /conversations/{id}/requests/{request_id}` 查回执(§8.2)。

**② 占用。** `sessions.reserve` 一步完成检查和占位(中间没有 `await`):
同一会话已有任何操作(运行、删除、文件清理、导出)报 409;全局运行数超过 `MAX_CONCURRENT_RUNS`(默认 4)报"同时运行的会话已达上限"。
会话还在等待清理(pending purge marker)也拒绝。占用从这里一直保持到收尾结束,不靠 Redis TTL。

**③ 校验。** 会话必须属于当前用户(并在此认领 owner,之后上传的文件才有归属);回退时目标必须是本会话的用户消息。
`full` 模式回退时,如果目标那一轮的文件快照不可用,直接报 `FilesUnavailable`,由用户明确选择 `conversation_only`。

**④ 上传。** 见 [02](02-文件上传与产物交付.md)。放在回退之前:上传失败时历史还没动。

**⑤ Run 落库。** 先推 `upload.complete`、`user.message` 两个事件,再写 `accepted` 的 Run(输入、附件、回退参数、请求指纹、trace id)。
从这一刻起,刷新页面的前端就能拿到 `prompt_id` 接回事件流。

**⑥ 启动后台任务**,返回 `prompt_id`。

**⑦⑧⑨ 后台准备。** 回退流程见 §5。之后 `run_store.start` 在一个事务里写入用户消息、选中的 checkpoint、恢复关联和所答 interrupt,
置 `input_committed`。**只有输入提交之后**才做本轮开始前的文件快照(§6),这样未被接受的输入不会挤掉保留的旧快照。快照失败只记 `snapshot_ready=false`,不阻止这一轮。

**接受阶段失败的收尾。** ⑤ 之后、任务启动前抛异常(包括请求被取消):如果 Run 已提交,按 `admission_interrupted` 记成 `cancelled`/`error`,
并给已写过事件的流补结束标记;占用随即释放。

**原则:所有可能失败的步骤放前面,破坏性的步骤放后面,且破坏性步骤要么可恢复、要么在提交凭据之后。** 这条在启动、交付文件(见 02)、备份导入(见 07)里反复出现。

## 3. 运行中

### 3.1 三种流同时订阅

`_run_agent` 用 LangGraph 的 `astream`,`stream_mode=["messages", "updates", "custom"]`:

| 流 | 内容 | 转成的事件 |
|---|---|---|
| `messages` | 模型逐 token 输出 | `ai.token` |
| `updates` | 每个节点完成后的状态更新 | `ai.tool_call`、`ask.user` |
| `custom` | 工具自己主动发的事件 | `tool.result`、`files.presented`、`widget.presented`、`sources.presented` |

细节:

- `messages` 流里会混进摘要、`view_image`、文档审阅等**工具内部的模型调用**,只转发节点名为 `model` 的主模型输出,
  否则这些内部文字会拼进回答。
- 带 `tool_call_chunks` 的片段不转发(那是工具调用的参数片段,不是给用户看的文字)。
- 文字每 5 个 token 合并成一个事件再发,减少事件数。遇到 `updates` 或 `custom` 事件前先把攒着的发出去,保证顺序正确。
- `files.presented` 里的 `host_path`(服务器上的绝对路径)发给前端前被去掉,也不落库。

### 3.2 边跑边落库

事件统一经过 `RunEvents`(`runtime/events.py`):附上 `run_id/seq/schema_version`,一边写进 Redis Stream,一边交给 `TurnRecorder` 攒成 assistant 消息的 `parts`。

遇到 `tool.result`、`files.presented`、`widget.presented`、`ask.user`、`sources.presented` 这几类**关键事件**时立刻保存一次进度(Run 状态 `running`);
此外后台 ticker 每 2 秒检查一次,有未保存的新事件就再存。所以长任务跑到一半进程崩了,已经完成的步骤、已交付的文件记录都在。

### 3.3 心跳和超时

ticker 每 30 秒推一个 `heartbeat` 事件,让前端区分"长工具调用"和"连接卡死"。会话互斥由 `RunHandle` 保证,不依赖任何 TTL。

流首次创建后,后续追加用 Redis 的原子存在性检查:流如果中途丢了(Redis 重启、被淘汰),不会被悄悄重建成缺了前半段的流,
而是标记 `transport_failed`,本轮以 `stream_unavailable` 结束,结果仍然落库。

两个时限:`LLM_REQUEST_TIMEOUT_SECONDS`(默认 180)控制单次模型 HTTP 请求;`AGENT_RUN_TIMEOUT_SECONDS`(默认 1800,0 关闭)控制一次执行的总时长。
超时都走正常的收尾,保存明确的错误。

### 3.4 向用户提问:`ask_user_input`

模型调用 `ask_user_input` 时,LangGraph 的工具内部触发 `interrupt`,图的执行暂停:

```
第 N 轮  模型 ─► ask_user_input ─► interrupt ─► 发 ask.user 事件 ─► 状态 waiting ─► 本轮结束
第 N+1 轮  用户的消息 ─► 检测到线程停在 interrupt 上 ─► Command(resume=答案) ─► 工具拿到答案继续
```

第 N+1 轮开始时 `_resume_command` 检查线程:有未回答的 interrupt,这条消息就是答案,用 `Command(resume=...)` 恢复;
没有,就当作普通新消息。

模型并行调用多个需要提问的工具时,会同时挂起多个 interrupt。界面**一次只展示最早的一个**,
答完再展示下一个。恢复时必须按 id 指定回答哪一个,而且要排除已回答的(它们仍留在快照的 interrupts 里,但对应的 task 已有结果),
否则会永远重复回答第一个。

### 3.5 结束

无论正常、出错还是取消,收尾都由同一个 `finalize()` 完成,并用 `complete_before_cancelling` 放进独立任务排空,收尾本身不会被再次取消打断。顺序是:

1. handle 进入 `finalizing`,停止 ticker,关闭 `astream`。关闭失败说明无法确认工具已停,记 `cleanup_failed` 并进入 `recovery_required`。
2. 检查沙箱 shell 是否"停止未确认"(见 [04 §4.4](04-专题-沙箱与命令安全.md)),是则记 `recovery_required`。
3. 回退操作如果还没完成,按 `input_committed` 决定前滚还是回滚(§5)。
4. 取消时给没有结果的工具调用补 "Execution cancelled by user."。
5. 发 `usage`、`error` 事件(通知失败不影响后续步骤)。
6. **在一个业务事务里**保存 Run 终态、assistant 快照和会话展示结果。终态保存最多重试 3 次;仍失败就进入 `recovery_required`,并推 `history_save_failed`。
7. 发 `stream.end`,把流 TTL 缩短为 5 分钟。
8. 释放占用。`recovery_required` 的 handle **不释放**:会话保持占用,新一轮、删除、回退都会被拒绝,直到重启服务。

**落库必须先于 `stream.end` 和释放占用。** 否则用户可以立刻发下一条,下一轮的用户消息会比本轮回答先落库,历史顺序就乱了。

出错时:预算超限、回退失败、resume 冲突的文案原样展示;其他异常只给通用提示和 trace id,详情留在日志里。

本轮有新交付的 Office 文件时,结束后在后台预转换(最多 3 个,见 02 §4)。放在本轮结束之后,不挡住 Agent 自己的命令。预热失败不影响本轮。

## 4. 取消

前端点"停止"调用 `POST /thread-cancel/<id>`,进入 `cancel_chat`:

1. 没有 handle:返回最新 Run 的状态,什么也不做。
2. 设 `cancel_requested`。任务还没建起来(接受阶段在复制大文件)时,最多等 30 秒;准备阶段会看到这个标志,在进入图之前停下。
3. 调用 `task.cancel()`。**等待任务结束**和"任务还没进入协程时的收尾"放进同一个独立任务,用 `complete_before_cancelling` 排空:
   取消请求本身被取消(用户关页面、连点停止),收尾也会跑完,占用不会留在半路。
4. 任务内部收到 `CancelledError`,走 §3.5 的统一收尾,Run 记为 `cancelled`。

**补"未完成"的工具调用有两种文案。** 用户取消时补 "Execution cancelled by user.";
出错、超预算、进程崩溃留下的悬空调用,在**下一轮开始时**兜底补 "Execution was interrupted before this tool call finished."。
后一种不能说成用户取消,否则模型会以为用户不想要这一步。等待用户回答的 interrupt 不算悬空,不补。

**沙箱命令要确认停下来。** 取消正在跑的 `bash_tool` 时,shell 由 sandbox-manager 杀掉并回执 `stopped`;
没收到回执或回执说没停,`SandboxStopUnconfirmed` 会穿过工具的错误处理(不会被包装成普通工具错误),
会话停在 `recovery_required`。宁可挡住用户,也不让一个可能还在写文件的进程和下一轮并存。

## 5. 回退与重发(编辑消息、重新生成)

用户编辑某条消息或点"重新生成"时,请求带 `rewind_to_message_id` 和 `rewind_mode`(`full` 或 `conversation_only`)。要回到的状态有三份:

| 对象 | 怎么回退 |
|---|---|
| ① 对话状态 | 每轮开始时记下该轮**之前**的 checkpoint id。回退只在 `Conversation` 上改选中的 thread/checkpoint,**不写图更新**;旧分支留在库里。目标在空图上(第一条消息)时换一个新 thread |
| ② 沙箱文件 | 恢复到那一轮开始前的 `output/` 和 `scratchpad/`(§6);`conversation_only` 时跳过 |
| ③ 数据库消息 | 截断该消息及之后的消息 |

`services/rewind.py` 把文件替换做成可恢复的:

```
预检目标和附件 ─► 快照复制到 staging ─► 写 journal ─► 旧目录改名为 backup,安装新目录
   ─► 业务事务:截断历史 + 写新用户消息 + 切换图选择(置 input_committed)─► 删 backup 和 journal
```

`input_committed` 是判定的凭据:提交前失败,把 backup 换回去;提交后失败,完成新状态的收尾。
启动时 `recover_operations` 扫描遗留的 journal 并按同样规则恢复,恢复动作可以重复执行。
安装新目录前先关闭会话 shell 并持有工作区锁,shell 的 cwd 不会指向被替换的目录。

文件快照不可用时**不会静默只回退对话**,而是报错让用户明确选择 `conversation_only`;缺失的上传原件也不会被自动忽略。
重发时沿用原消息的附件,不需要重新上传。

### 5.1 回退到"回答过提问"的那一轮

如果目标那一轮之后图停在一个已回答的 interrupt 上,旧答案及其子图结果还在同一 checkpoint 的 pending writes 里,直接选中会把旧答案带回来。
`agents/recovery.py::fork_answered_interrupt` 用 checkpointer 公共 API 把历史复制到新 thread,定位 root 和嵌套图的暂停点,
只清掉**目标及之后**回答的那些 interrupt 的答案和被中断任务结果,保留已完成的兄弟任务和更早的答案。
"哪些答案在目标之后"来自每个 Run 记录的 `answered_interrupt`;旧数据没有这个记录时按旧行为清掉同一暂停点的全部答案。
复制后从新 thread 头恢复,而不是显式 replay(那会重放已完成的并行任务)。复制目标先记进 journal,未提交时删除临时 thread。

## 6. 文件快照

回退要恢复文件,所以每轮开始前给 `output/` 和 `scratchpad/` 做一份快照(`uploads/` 只读,不用备份)。

- 存在 `sessions/<id>/snapshots/`,不在 bwrap 挂载内,Agent 碰不到。
- 目录名是 20 位补零的纳秒时间戳加 `_` 和 `prompt_id`,按名字排序就是按时间排序;回退时靠 `prompt_id` 找到对应的那份。
- **去重**:先算一个内容清单指纹,内容是各文件的路径、类型、权限、大小、mtime。
  与最新一份相同(这轮之前没人改过文件)时,用硬链接复制(`cp -al`),几乎不占空间。
- **原子性**:先写到临时目录再改名,复制中途失败不会留下残缺的快照。
- 清单不含 `_preview`、`_rag`、`_review` 这几个系统临时目录,它们不属于用户内容。
- **上限**:两个目录合计超过 300 MB(`SNAPSHOT_MAX_MB`)就跳过这一轮;只保留最近 3 份(`SNAPSHOT_KEEP`)。

**恢复**:按 §5 的 staging → journal → 替换流程把快照复制回来,快照目录本身不动;新一轮输入提交后才做新快照并裁剪到最近 3 份。
替换前关掉会话 shell(它的工作目录可能在被替换的目录里)。

**找不到快照**(被淘汰、当时太大、旧会话,或 `snapshot_ready=false`)时,`full` 回退会被拒绝,用户可以选择仅回退对话、保留当前文件。

### 6.1 例子:连续改三次之后回到第二轮

```
第1轮  生成 report.docx(v1)       快照S1 = 空
第2轮  修改为 v2                   快照S2 = {report.docx v1}
第3轮  修改为 v3                   快照S3 = {report.docx v2}

用户编辑第2轮的消息 ─► 用 S2 替换工作区 ─► output/report.docx 回到 v1
                                  对话回到第2轮之前,数据库里第2、3轮的消息被截断
                                  新一轮提交后做快照S4,只保留最近 3 份
```

## 7. 产物版本和快照的区别

| | 快照 | 版本 |
|---|---|---|
| 回答的问题 | 回到某一轮之前,整个工作区什么样 | 这个交付给用户的文件,以前是什么内容 |
| 触发 | 每轮开始前自动做 | 每次 `present_files` 覆盖同名文件时 |
| 数量 | 最近 3 轮 | 每个文件最近 5 份 |
| 用途 | 回退、重新生成 | 旧消息的下载链接、对比 |

两者独立:版本保存在 `versions/` 里,**不受回退影响**。回退到第 2 轮后,第 3 轮交付的 v3 版仍可通过历史链接下载。
版本的细节见 [02 §3.2](02-文件上传与产物交付.md)。

## 8. 事件流、断线续传和重启恢复

### 8.1 服务端

每个 `prompt_id` 一个 Redis Stream。`POST /stream-events` 带 `start_id`,服务端先校验这个 Run 属于该会话和当前 owner,
再从 `start_id` 之后读取。读不到新事件时最多阻塞 `block_ms` 后结束这次响应,由前端重新发起。
**流已过期或丢失时返回 410**,前端据此改查持久的 Run。

| 对象 | 保留 | 说明 |
|---|---|---|
| Redis 事件流 | 运行中每次写入续期 1 小时;结束后 5 分钟 | 过期后靠 SQLite 还原 |
| `GET /runs/{run_id}` | 持久 | 状态、错误、已保存的 `parts` 和 `seq` |
| `GET /conversations/{id}/requests/{request_id}` | 持久 | 发送响应丢失后查原请求对应的 Run |

应用层 `seq` 和 Redis 条目 id 用途不同:条目 id 是 XREAD 游标,`seq` 用于应用层去重和对齐快照。

### 8.2 前端重连(`frontend/src/api/client.ts`)

**发送。** `sendMessage` 只重试没拿到 HTTP 响应的网络错误,所有重试共用同一个 `client_request_id`:

- 第一次就被服务端拒绝(4xx/5xx):确定被拒,直接报错。
- 前面已有结果未知的尝试,之后的重试被拒:不能说明第一次没被接受。抛 `SendUncertainError(retryRejected)`,
  `stores/chat.ts` 按 request_id 轮询回执(6 次 × 500 ms);查到就接上那个 Run,查不到就提示"无法确认消息是否已发送",**保留界面上的消息**,不回滚。

**读流。** 前端记下每个事件的条目 id,断了就从断点继续读;`run.snapshot` 替换该 Run 的展示内容,`seq` 过滤已消费的事件。

| 情形 | 处理 |
|---|---|
| 服务端正常结束了一次响应(空闲 `block_ms`) | 带着 `lastId` 立刻重连 |
| 60 秒没收到任何字节 | 视为卡死,主动断开并重连,**不算失败** |
| 网络错误或 5xx | 指数退避重试:500 ms、1 s、2 s、4 s、8 s(上限 8 s) |
| 连续失败或连续空响应 5 次 | 查 `GET /runs/{id}`:已终态就载入快照并结束;仍在 `preparing/running/finalizing` 就继续等 |
| 410(流过期或丢失) | 载入已保存的进度;终态就结束,否则稍后再查,等收尾落库 |
| 4xx(408、429 除外) | 直接报错 |
| 收到 `stream.end` | 结束 |

### 8.3 刷新页面

前端用 `GET /thread-status/<id>` 拿到运行状态和当前 `prompt_id`,再用 `start_id = 0-0` 接回事件流,
从头回放,界面就恢复到当前进度。流已过期时,历史由 SQLite 里的消息还原。

### 8.4 进程重启和关闭

**启动时**依次:恢复遗留的回退 journal(`recover_operations`),再 `recover_interrupted`:
凡是 Run 仍在 `preparing/running/finalizing` 的,其任务属于已退出的进程。处理:

- 图已经持久停在一个提问上、但 `ask.user` 还没进展示历史:从 checkpoint 重建提问,Run 记为 `waiting`,用户可以直接回答。
- 其他情况:保留已落库的进度,Run 记为 `error`(`process_interrupted`,"服务重启,本次生成已中断")。

重启后**不会自动重放**任何 bash 或 MCP 调用。下一轮开始时补齐悬空的工具调用(§4)。

**关闭时**先停止接受新任务,再等待准备中的提交、文件/删除操作、Run 收尾和辅助转换,最后关闭 shell、客户端和数据库。

## 9. 局限

- `RunHandle` 和会话占用在进程内存里,只能单进程部署。
- 重启时被中断的那一轮,已落库的步骤保留,之后的内容丢失;不会自动续跑。
- `recovery_required` 需要重启服务才能解除,没有在线的"确认已停止"入口。
- 事件流在 Redis 里只保留有限时间(结束后 5 分钟),之后靠 SQLite 里的消息还原。
- 快照最多 3 份、合计不超过 300 MB;快照不可用的轮次只能选择仅回退对话。
- checkpoint 不会回滚 MCP 等外部副作用。

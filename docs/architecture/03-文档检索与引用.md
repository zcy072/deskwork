# 03 文档检索与引用

Deskwork 的文档检索不是"每次提问都先检索再生成"的固定流水线(传统 RAG)。
检索是 Agent 的一个**工具** `search_document`,调不调用、搜什么词、搜几次,都由模型自己决定。
工具描述里给了使用建议:

| 场景 | 建议 |
|---|---|
| 文件很长(几千字符以上),要查具体事实(人名、数字、条款) | 用 `search_document` |
| 文件短 | 直接 `view_file` 读全文 |
| 要统计、汇总全文 | 检索帮不上,改用 bash / python 处理文件 |

这个设计的好处是:简单问题不付检索成本;检索词不对时,模型能看到"没有找到"并换词重搜,
而不是拿着一堆不相关的段落硬答。

本文分两部分:前半讲怎么找到相关段落(§1–§5),后半讲怎么保证"引用的原文是真的"(§6–§7)。

## 1. 一次检索的流程

参数:文件路径、关键词 `query`、返回段数 `top_k`(默认 5,范围 1–10)。

```
search_document(path, query, top_k)
   │
   ├─ ① get_index:取(或现建)这个文件的索引      ← 内存缓存,见 §5
   │      文本提取 → 切块 → 建 BM25 索引 →(可选)给每块算向量
   ├─ ② search_index:关键词打分,取前几段          ← §3、§4
   ├─ ③ source_references:为每段生成引用来源       ← §6
   ├─ ④ format_results:拼成给模型看的文本
   └─ ⑤ 发 sources.presented 事件,让前端登记这些来源
```

返回给模型的文本长这样(示意):

```
共 38 段,返回最相关的 2 段:

[段 12 | 偏移 5830 | 分数 4.217]
引用链接:[原文 · 第 3 页](#source-9f2c…)
第三条 合同金额为人民币 120 万元整……
```

两点说明:

- **出错不抛异常**。检索失败时返回一条 `Error: …` 的工具结果给模型,不会打断 Agent 的这一轮。
- **没有命中**时返回"没有找到相关段落,换用原文中可能出现的词再搜,或确认文档确实没有该内容",
  引导模型换词或如实告诉用户,而不是编造。

索引是**按需建、放在进程内存里**的:没有离线入库,也没有持久化的向量库。后端重启后索引要重建。
这是和传统 RAG 最大的区别:没有"入库"这个阶段,文件上传后第一次被搜索时才处理。

## 2. 文本提取和格式

提取方式见 [02 §2](02-文件上传与产物交付.md),这里只说和检索有关的部分。

- 可检索的类型:`txt md csv json log tsv`(直接读)和 `pdf docx pptx xlsx doc xls ppt html`(先在沙箱里转换)。其他扩展名报"不支持检索"。
- 全文超过 500 万字符拒绝建索引("文档过大")。
- **转换是在沙箱里跑的**:不可信文件的解析代码不放在后端进程里。每次转换用一个随机文件名写到
  `scratchpad/_rag/`,后端读回后立刻删除。随机文件名是为了让并行转换同一个文件的不同版本时,互不覆盖。
- 转换完成后会**再算一次文件指纹**,和转换前对比。不一致说明检索期间文件被改了,直接报
  "检索期间文件发生变化,请重新检索",不会拿半新半旧的内容建索引。

## 3. 切块与分词

### 3.1 切块

目标:每块约 500 字符,尽量按行边界切,让一块是一段完整的话。

规则(`split_chunks`):

1. 按换行拆成行,空行丢弃。
2. 依次把行加进当前块;**再加这一行会超过 500 字符时**,先把当前块收尾,再开新块。
3. 单独一行就超过 500 字符(例如一整段没有换行的长文),按 500 字符硬切。
4. 每块记录:在全文中的字符偏移、起止行号。

PDF 和 PPTX 按页/幻灯片**分别**切,所以块不会跨页。这样每块都能对应到准确的页码。
编号从 1 开始,空白页也占号,保证页码和原文件一致。

举例:一个 3 页的 PDF,第 1 页 300 字,第 2 页 1100 字(没有换行),第 3 页空白。

| 块 id | 来源 | 内容 |
|---|---|---|
| 0 | 第 1 页 | 300 字 |
| 1 | 第 2 页 | 前 500 字 |
| 2 | 第 2 页 | 中间 500 字 |
| 3 | 第 2 页 | 剩余 100 字 |

第 3 页是空白,不产生块,但页码 3 仍被占用。

### 3.2 分词

检索要把文本变成"词"。英文有空格,好办;中文没有空格,通常要分词词典。
这里**不用词典**,用一种简单做法:

- 英文、数字:按连续的字母数字片段,统一小写。
- 中文:拆成**单字**,再加上**相邻两字**。

示例:

| 原文 | 词(tokens) |
|---|---|
| `合同金额` | 合、同、金、额、合同、同金、金额 |
| `Q3 revenue 增长` | q3、revenue、增、长、增长 |

原理:不管词典怎么切,只要查询里的词和原文里的词有相同的字或相邻字对,就能匹配上。
搜"金额"能命中"合同金额",因为都含有"金额"这个字对。

代价有两个,都是这个做法本身带来的:

1. **不理解同义词**。"报酬"拆成 报、酬、报酬,"薪资"拆成 薪、资、薪资,没有任何交集,搜不到。
   这时靠模型换词重搜,或者开启向量检索(§4)。
2. **单字会带来噪声**。搜"合同金额"也会给只含"金额"二字的段落加分(比如"报销金额")。
   但字对"合同""同金"只有真正出现这个词的段落才有,所以相关的段落分数仍然更高。

## 4. 打分:BM25,以及可选的向量检索

### 4.1 BM25 怎么给一段话打分

BM25 是经典的关键词相关度公式。对每个查询词,它看三件事:

1. **这个词稀不稀有(idf)**。只在少数段落里出现的词,区分力强,权重高;到处都有的词权重低。
   公式 `ln(1 + (N − df + 0.5) / (df + 0.5))`,N 是总段数,df 是含该词的段数。
   例:共 100 段,某词只在 2 段出现,idf ≈ 3.70;某词在 50 段出现,idf ≈ 0.69。
2. **这个词在这段里出现几次(tf),但收益递减**。出现 1 次得 1.00 分(相对值),3 次 1.67,10 次也只有 2.17。
   防止一段话靠反复堆同一个词拿高分。
3. **这段话长不长**。同样出现一次,短段落比长段落更能说明相关,所以按段长相对平均段长做惩罚。

代码里的参数 `k1=1.5`(控制第 2 点的递减速度)、`b=0.75`(控制第 3 点的惩罚力度)是业界常用默认值。
一段话的总分是各个查询词得分之和;得分为 0(一个查询词都没命中)的段落不返回。

实现上是对所有块**线性扫描**,没有倒排索引。单个文档最多 500 万字符,约一万块,扫描够快;
而且每个索引只服务一个文件,没必要引入更复杂的结构。

### 4.2 可选的向量检索

BM25 只认字面,搜"报酬"找不到"薪资"。向量检索把文字转成数字向量,意思相近的文字向量也接近,可以补上同义词这一块。

**默认关闭。** 同时配置了 `EMBEDDING_API_KEY` 和 `EMBEDDING_BASE_URL` 才启用,调用 OpenAI 兼容的 `/embeddings`
接口(默认模型名 `BAAI/bge-m3`)。启用后,被检索文档的文字会发送给这个外部服务,
所以由使用者自己决定要不要开。

细节:

- 建索引时批量向量化,每批 32 段,最多 4 批并发,单次请求超时 60 秒。
- 段数超过 2000(`EMBEDDING_MAX_CHUNKS`)就不做向量,只用 BM25,避免大文档的向量化成本失控。
- 向量的范数在建索引时预先算好,检索时不再重复开方。
- **任何一步失败都自动退回纯 BM25**:建索引时向量化失败,这个索引就没有向量;
  查询词向量化失败,这一次检索只用 BM25。检索不会因此报错。

### 4.3 RRF:怎么合并两个排名

启用向量后,有两份排名:BM25 的前 20 名,向量相似度的前 20 名。要合成一份。
BM25 的分数是 4.2 这种量级,余弦相似度是 0.82 这种量级,不能直接相加。

RRF(倒数排名融合)的做法是**只看名次,不看分数**:每一路里,排第 r 名的段落得 `1 / (60 + r)` 分,
几路的得分相加。常数 60 让靠前几名之间的差距不会太悬殊。

示例:BM25 排名是 A、B、C,向量排名是 C、A、D。

| 段落 | BM25 名次 → 得分 | 向量名次 → 得分 | 合计 |
|---|---|---|---|
| A | 第 1 名 → 1/61 = 0.01639 | 第 2 名 → 1/62 = 0.01613 | **0.03252** |
| C | 第 3 名 → 1/63 = 0.01587 | 第 1 名 → 1/61 = 0.01639 | **0.03226** |
| B | 第 2 名 → 1/62 = 0.01613 | 没上榜 | 0.01613 |
| D | 没上榜 | 第 3 名 → 1/63 = 0.01587 | 0.01587 |

融合结果:A、C、B、D。

可以看到:两路都靠前的 A 和 C 排到最前;只有一路靠前的 B、D 排在后面。
这正是我们要的效果,字面和语义都认为相关的段落最可信。

需要注意融合后返回的"分数"是 RRF 分(0.03 量级),不是 BM25 分,两者不能比较。

## 5. 索引缓存

建索引要做文本转换、切块、(可选)调向量接口,代价不小,所以缓存起来:

- 缓存最近用过的 **8 个**文件的索引(LRU,满了淘汰最久没用的)。
- 缓存键是 (会话, 路径, 文件状态)。文件状态包括 mtime、ctime、大小和 inode,
  文件一被改写,旧索引就不会再命中。
- **合并并发构建**:模型在同一轮里可能同时发起两个对同一文件的检索。第二个请求发现已有构建任务在跑,
  就等它,而不是重复转换、重复调用向量接口。某个调用方被取消,不会打断其他在等同一份索引的调用方。

## 6. 引用:怎么保证"引用的原文是真的"

这是本模块最有特点的部分。问题是:模型回答"合同金额为 120 万元(见第 3 页)",用户凭什么相信?
模型可能记错页码,甚至编一个来源。

### 6.1 每个检索结果带一条来源

来源包含:文件名、**文件内容的 SHA-256 指纹**、位置、该段原文摘录,以及一个来源 id。
来源 id 由"文件路径 + 指纹 + 块 id"算 SHA-256 取前 24 位,所以文件变了,同一段的 id 也变。

位置的表示按文件类型而不同:

| 文件类型 | 位置 | 链接文字 |
|---|---|---|
| PDF | 页码 | 原文 · 第 3 页 |
| PPTX | 幻灯片编号 | 原文 · 第 5 张幻灯片 |
| DOCX | 段号(非空段落计数,整张表格算一段) | 原文 · 第 12–14 段 |
| 文本类 | 行号区间 | 原文 · 第 40–52 行 |

只有位于 `uploads/` 或 `output/` 的文本、PDF、PPTX、DOCX 才生成来源。
xlsx、html 等可以检索,但结果没有引用链接。

DOCX 的段号是这样来的:转换时每个非空段落输出为一行,所以"行号"就是"段号"。
Word 本身没有可靠的页码概念(页码取决于渲染),按段落计数是稳定的替代。

### 6.2 指纹在哪里被检查

为了保证"建索引时读的内容"和"生成引用时的文件"是同一份,指纹在建索引前后各算一次,不一致就报错重来。

模型被要求把引用链接**原样**贴在对应论断旁边,不得编造 id 或页码。前端再加两层约束:

**第一层:只打开登记过的来源。** 模型回答里的链接形如 `#source-9f2c…`。
前端点击时,在本会话已收到的 `sources.presented` 事件里查这个 id(`knownSources`)。
模型编造的 id 查不到,点击后什么也不会打开。较早轮次检索到的来源也在这个表里,后续回答可以引用。

**第二层:文件变了就拒绝。** 点击后前端请求原文件时带上当时的指纹。服务端读出文件字节,重新算 SHA-256:

- 一致:返回文件。
- 不一致:返回 409,前端显示"原文件已变化,无法定位这条旧引用。请重新检索文件。"

校验用的字节和返回给浏览器的是**同一份**,所以校验之后文件再被改写,也不会出现"校验通过但内容错位"。

示例:用户上传 `合同.pdf`,模型检索后引用"第 3 页"。之后 Agent 又把 `合同.pdf` 改写了。
用户再点这条旧引用,指纹对不上,得到 409,而不是看到一个第 3 页内容已经变了的 PDF。

### 6.3 预览怎么展示

| 类型 | 展示 |
|---|---|
| PDF | 在 iframe 里打开,并跳到对应页(`#page=N`) |
| PPTX、DOCX | 展示检索时的摘录,并提供原文件下载(已验证文件未变) |
| 文本类 | 显示命中的行,前后各带 3 行上下文,命中行高亮 |

所有类型的弹窗顶部都先显示"检索时的摘录",即使原文件之后变了,用户也能看到模型当时读到的文字。

## 7. 局限

- 没有 OCR,扫描件检索不到内容。
- 关键词匹配,不懂同义词;只有配置了 embedding 才有语义召回。
- 一次只检索一个文件,跨文件要模型多次调用。
- 不能统计或汇总全文,这类问题要用 bash / python。
- 索引只在内存里,重启丢失;只缓存最近 8 个文件。
- 引用只覆盖 `uploads/`、`output/` 里的文本、PDF、PPTX、DOCX。
- DOCX 的页眉页脚、脚注、批注、文本框不在索引里,也就搜不到。

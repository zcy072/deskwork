# 07 专题:会话备份、导入与用量统计

一个会话包含消息、文件和 Agent 的对话状态(checkpoint)三部分。本文说明它们怎么被打成一个备份包、
怎么安全地导回来(`services/session_export.py`、`session_import.py`、`checkpoint_transfer.py`),以及一轮对话的 token 用量怎么统计。

## 1. 备份包里有什么

导出得到一个 zip:

| 条目 | 内容 |
|---|---|
| `manifest.json` | 格式版本、导出时间、每个文件的 sha256 和大小、被跳过的文件及原因、消息里引用但磁盘上已不存在的文件、checkpoint 信息 |
| `conversation.json` | 标题、全部消息(含 `parts`、用量、状态)、用户消息的附件和 checkpoint id;v4 起还有每个 Run 的状态与轮次,以及会话选中的图 thread/checkpoint |
| `files/uploads/...`、`files/output/...` | 实际文件 |
| `checkpoint.json` | LangGraph 的 checkpoint 与 writes 原始行(base64),导入后可以接着原上下文继续对话 |

**不含**历史版本(`versions/`)和回退快照(`snapshots/`),`scratchpad` 也不导出,只导出 `uploads` 和 `output`。

导出的几个细节:

- **符号链接一律不收。** `uploads`、`output` 对 Agent 可写,Agent 可以放符号链接指向宿主机上的文件。目录遍历跳过链接,
  读文件时用 `O_NOFOLLOW` 打开,并确认是普通文件。
- **边读边算 sha256。** 复制进 zip 的同时计算摘要,超过单文件上限(200 MB)中途就中止。
- **已经压缩过的格式不再压缩。** docx、xlsx、pptx、图片、zip 等用 `ZIP_STORED`,其余用 deflate。再压缩一遍只费 CPU。
- **上限。** 最多 5000 个文件、单个 200 MB、合计 1 GB。超出的文件不会让导出失败,而是记进 `skipped` 并写明原因。
- **缺失文件单独列出。** 遍历消息里的附件和交付文件,找出引用了但磁盘上没有的,记进 `missing`,恢复时一眼能看出缺什么。
- 临时 zip 放在系统临时目录。下载中途断开时 `FileResponse` 不会执行清理,所以后端每次启动时会删除超过 1 小时的遗留备份包。

## 2. checkpoint 的导出

`checkpoint_transfer.export_thread` 直接读 LangGraph 的 SQLite 表(`checkpoints` 和 `writes`)里属于这个会话的原始行,
二进制字段转成 base64。不经反序列化,所以导出内容与库里逐字节一致。

只支持 `AsyncSqliteSaver`;换成别的 saver 时导出会省略 checkpoint,原因记在 manifest 里。
超过 2 万行或 150 MB 时 `export_thread` 抛 `CheckpointRejected`,导出接口捕获后把原因写进 manifest,消息和文件照常导出。

## 3. 导入:把备份包当不可信输入

备份包是用户上传的,文件头注释把它列为不可信数据。导入**总是新建一个会话**,不覆盖任何已有会话。校验分几层:

**结构校验(`inspect_archive`,只读,不写任何东西):**

- 必须有 `manifest.json` 和 `conversation.json`,没有重复条目,条目数不超过上限。
- 格式版本必须在支持列表里(目前 1～4;v4 起携带 Run 元数据、输入是否已提交和选中的 checkpoint)。
- 每条消息:角色只能是 user / assistant,状态在白名单内,各字段有长度上限。导出时不会有生成中的会话,
  所以包里如果还有 `running` 状态,说明那一轮没正常结束,导入时改成 `error`。
- 文件路径逐段检查:不接受绝对路径、`..`、反斜杠、空字节,第一段必须是 `uploads` 或 `output`,
  而且拼回去必须与原字符串完全一致(拒绝不规范写法)。
- 每个文件的大小和 sha256 格式合法,zip 里确实有对应条目,总量不超过会话存储配额。

**写入校验(`extract_files`):**

- 不信 zip 头里声明的大小。解压时按实际读到的字节数累计,超过 manifest 声明的大小就中止。
- 写完后对照 manifest 的大小和 sha256,任何不一致都拒绝。
- 目标文件用 `O_CREAT | O_EXCL | O_NOFOLLOW` 创建。目录只由我们创建,会话是全新的,不会有 Agent 放进去的符号链接。
- `output` 目录设为可写权限(沙箱里的 Agent 要继续写),`uploads` 对 Agent 保持只读。

**事务性:** 先写文件和 checkpoint,最后用一个数据库事务写会话和消息。失败时清掉前面写的内容,会话不会半途出现。

## 4. 为什么 checkpoint 要特别小心

LangGraph 读取 checkpoint 时,会按数据里写的模块名去 import 并调用构造函数。注释(`checkpoint_transfer.py` 文件头)的判断是:
不可信的备份可以借此执行任意代码。

所以导入时先过一道类型白名单:

- 数据类型只接受 `msgpack`、`null`、`bytes`、`bytearray`。`json` 和 `pickle` 在读取时有各自的执行风险,不接受。
- 用 LangGraph 自己的安全类型白名单,逐层检查 msgpack 里的扩展类型(构造函数、pydantic 对象等),**只检查,不执行任何构造**。
  不在白名单里的,整份 checkpoint 都拒绝。

**版本兼容检查**也比较保守(`checkpoint_incompatibility`)。只有同时满足下面两点才会恢复 checkpoint:

- 备份里的图结构版本(`GRAPH_VERSION`)与当前一致。注释写明:修改 Agent 的节点或状态结构、或 checkpoint 恢复语义时才递增,改提示词不用。
- `langgraph`、`langgraph-checkpoint`、`langgraph-checkpoint-sqlite`、`langchain`、`langchain-core` 五个包的版本与备份时**完全相同**。
  注释说得直接:不推断补丁版本必然兼容。

不满足时不会整个导入失败,而是降级:保留消息和文件,丢掉 checkpoint,并给出警告
"不能接续原上下文或回退"。用户仍然可以查看历史和下载文件。

还有一种部分丢失的情况:某些消息记录的 checkpoint id 不在备份包里,这些消息单独失去"回退/重新生成"的能力,同样给出警告和数量。

## 5. 用量统计

`UsageTracker`(`services/usage.py`)累计一轮里所有模型调用的 token:调用次数、输入、输出、缓存命中的输入,以及按模型分组的明细。

一个容易出错的点:流式加 `updates` 模式下,同一条 AI 消息可能被看到多次。所以统计时按消息 id 去重,同一条只计一次。
回退到备用模型时 `models` 列表里会出现多个模型名,`by_model` 分开记账。

`BudgetGuard`(见 [04 §9](04-专题-沙箱与命令安全.md))用的就是它的累计值。统计结果随 assistant 消息一起落库
(`usage` 字段),会话级汇总由 `aggregate_usage` 把多轮的结果相加。配置里的预算默认值也有出处:
注释写明取的是评测中观察到的最大消耗(19 次调用、81.7 万 token)再留出余量,目的是拦死循环而不是限制正常长任务。
